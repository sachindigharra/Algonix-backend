┌──────────────────────────────────────────────────────────────────────────────┐
│ 5 DESIGN PATTERNS USED                                                       │
└──────────────────────────────────────────────────────────────────────────────┘

1. STRATEGY PATTERN
   ├─ Problem: Each platform has different API
   ├─ Solution: Interface + Multiple implementations
   ├─ Benefit: No if-else chains, easy to add platforms
   └─ Example: CodingPlatformService interface with LeetCode, Codeforces, etc.

2. FACTORY PATTERN
   ├─ Problem: Need to route to correct service
   ├─ Solution: Factory returns correct service based on platform type
   ├─ Benefit: Decoupling, centralized routing
   └─ Example: factory.getService(LEETCODE) → LeetCodeService

3. FACADE PATTERN
   ├─ Problem: Connect profile needs many steps (validate, fetch, parse, save)
   ├─ Solution: One service orchestrates everything
   ├─ Benefit: Simple controller, consistent business logic
   └─ Example: integrationService.connectProfile(userId, request)

4. REPOSITORY PATTERN
   ├─ Problem: Data access logic scattered
   ├─ Solution: Repository interfaces abstract database access
   ├─ Benefit: Testable, flexible, maintainable
   └─ Example: profileRepo.findByUserIdAndPlatform(userId, platform)

5. TEMPLATE METHOD PATTERN
   ├─ Problem: All platforms follow same sync process
   ├─ Solution: Base class defines steps, subclasses implement details
   ├─ Benefit: Code reuse, consistency
   └─ Example: BasePlatformService.sync() defines structure

┌──────────────────────────────────────────────────────────────────────────────┐
│ SYNC STRATEGIES                                                              │
└──────────────────────────────────────────────────────────────────────────────┘

STRATEGY 1: ON-DEMAND (User clicks "Refresh")
└─ Pros: Real-time data when user needs it
└─ Cons: Slow, rate limit issues
└─ Use when: User actively wants fresh data

STRATEGY 2: PERIODIC (Every 6 hours)
└─ Pros: Data always fresh, no user wait
└─ Cons: Costs API calls, DB load
└─ Use when: Frequent syncs acceptable

STRATEGY 3: HYBRID (Recommended) ✅
├─ Show cached data if sync < 30 min old
├─ Otherwise, trigger async background refresh
└─ And every 6 hours, batch sync all active users
└─ Pros: Fresh data, no excessive API calls
└─ Cons: Slight complexity in caching logic

┌──────────────────────────────────────────────────────────────────────────────┐
│ ERROR HANDLING SCENARIOS                                                     │
└──────────────────────────────────────────────────────────────────────────────┘

SCENARIO: Invalid Username
├─ Error: "Username not found on platform"
├─ Action: Mark profile as DISCONNECTED
└─ User action: Verify and retry

SCENARIO: Network Error
├─ Retry: Exponential backoff (1s, 2s, 4s, 8s)
├─ After max retries: Mark as PENDING
└─ User sees: Stale data with "sync pending" badge

SCENARIO: Rate Limited
├─ Action: Backoff for reset duration
├─ Queue: Sync for later
└─ Continue: Other platforms

SCENARIO: Partial Sync Failure
├─ Profile saved ✓
├─ Problems saved ✓
├─ Contests failed ✗
├─ Action: Save progress, retry contests next sync
└─ User sees: Partial update message

┌──────────────────────────────────────────────────────────────────────────────┐
│ COMMON MISTAKES TO AVOID                                                     │
└──────────────────────────────────────────────────────────────────────────────┘

❌ DON'T: Hardcode platform logic in controller
✅ DO:    Use Strategy pattern → interface + implementations

❌ DON'T: Call database directly from controller
✅ DO:    Use Repository pattern → repositories abstract access

❌ DON'T: Have multiple sync methods scattered everywhere
✅ DO:    Use Facade pattern → one entry point (PlatformIntegrationService)

❌ DON'T: Ignore API rate limits
✅ DO:    Implement retry with exponential backoff, queue mechanism

❌ DON'T: Store API keys in code/config files
✅ DO:    Use environment variables or AWS Secrets Manager

❌ DON'T: Sync all users on every request
✅ DO:    Use hybrid strategy → cache + background scheduler

❌ DON'T: Fail entire sync on one platform error
✅ DO:    Implement partial sync → save what succeeded, retry failed parts

❌ DON'T: Skip validation of external data
✅ DO:    Validate all data before saving to DB

❌ DON'T: Miss tests for your code
✅ DO:    Write unit, integration, and API tests
